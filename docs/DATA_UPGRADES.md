# 安装升级与历史记录 · 2026-11-25

## 新IPA安装后是否保留

在iOS把它识别为现有GymRest的**覆盖更新**、应用数据容器保留、数据库升级成功的条件下，已有计划、训练历史、健康运动关联及未完成训练通常会继续存在。不能把“IPA文件相同名称”当作同一应用身份的证明。

项目当前主Bundle ID固定为 `dev.gymrest.personal`，扩展为 `dev.gymrest.personal.widgets`。HealthKit可选构建不改这些ID。SideStore可能重写签名后的标识，所以应保持同一Apple ID/签名团队和现有App身份，通过现有GymRest的更新流程安装；若被安装为另一个GymRest，可能是独立数据容器。

- **不要先卸载再安装**：删除App通常会删除其本地数据。没有云同步可自动找回。
- **不要将改Bundle ID或换签名账号视为普通升级**：可能安装到新容器或要求先移除原App。
- **签名到期不等于主动清库**：代码不会因签名过期而删除数据，但App可能暂时无法启动，需要正确续签。
- **旧版没记录过的历史不能补生成**：阶段一版本没有训练历史，升级不会还原当时未保存的数据。

## 已核对的代码

生产App使用默认持久化SwiftData容器，没有内存模式、升级时删除数据库或自动清空TrainingRecord的逻辑。默认模板只在偏好记录缺失时初始化，未删除既有历史。结束训练只清理ActiveTraining并归档快照；修改或删除源计划不级联删除历史。历史删除是用户在记录列表主动执行的操作。

0.4.0新增TrainingProgram和可空programID；此前新增的逐组动作名称等字段也是可选。现阶段依赖SwiftData的自动轻量迁移，**没有获得0.3.x真实数据库升级到0.4.0的真机验证证据**。即使代码没有清库，迁移失败也可能导致数据暂时无法读取，因此不能保证百分之百无风险。

本轮将异常“当前训练快照”与整个数据库错误分离：快照校验/解码异常时保留它，阻止开始新训练和提醒测试，允许查看计划/历史并重试恢复；真正数据库I/O错误仍显示存储错误页，不伪装为仅进度异常。不自动清库。

## 备份缺口与后续优化

目前JSON导出**只包含计划、训练日、动作和替代项，不包含训练历史、当前训练和健康关联**。导出计划不能作为历史备份。当前没有完整应用数据导出/恢复功能，因此不要为排错直接卸载。

优先建议：

1. 增加独立的完整本地备份/恢复，明确区分计划分享文件和私人历史数据。
2. 引入显式VersionedSchema与SchemaMigrationPlan，并保存真实旧版数据库fixture，持续验证跨版本升级；本次不贸然改存储路径或重建数据库。
3. 记录积累后为历史列表增加分页/日期筛选；详情内逐组名称已改为每次渲染只解码一次。

## 新增测试及证据边界

DiskPersistenceTests新增3项：使用真实临时文件数据库，写入后创建新ModelContainer读回，检查历史/计划/偏好/健康关联、活动训练共存、删除源计划后历史快照保留。它们尚未在Xcode执行；即使通过，也只证明同版本容器重开，不能替代真实旧版本迁移或SideStore覆盖升级测试。

RecoveryProtectionTests新增3项：坏进度不阻止读取计划、开始/结束不能覆盖坏进度、失败重试保留数据及有效状态重新载入。这些也尚未执行。iOS XCTest目前总62项；本地6个Python回归和静态检查通过，不代表iOS升级验证通过。

本轮及前轮优化仍保留工作区，未再次提交/推送/触发构建。
